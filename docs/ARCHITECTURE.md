# Architecture

Unlease is a suite of apps that replace Google's, on a server you run: stop leasing your data to Google, and unleash yourself. Carnet (notes, checklists, drawings, collections of links, pages) is the first; a calendar and contacts are meant to follow. Below, `core/x`, `design/x` and `notes/x` are `packages/<name>/src/x`.

## One repository, apps installed one by one

Everything is in one repository, because the apps share the sync, the design system and data that points from one app into another: a change to any of them is one commit, tested against every app at once, and nothing is published between them. Proton keeps Mail, Calendar and Drive's web apps in one repository for the same reasons (their move from many is told in [their engineering blog](https://proton.me/blog/engineering-polyrepo-monorepo)); Ente keeps its photos and authenticator apps and their server together. Folders follow the toolchains, as Ente's do:

| Where | What |
| --- | --- |
| `packages/core` | The platform: records and their merge, the sync protocol and engine, ids, references, rich text, the dictionary machinery, formatting, the search engine, the apps' registry (`apps.ts`). |
| `packages/design` | The design system's data, the same for every app: palette, appearance, continuous corners, the pebble, outlines, Onde's glyphs, emblems, collages, the mark, Signika's advance widths and line wrapping. |
| `packages/notes` | Carnet's domain: its record types (`sync/types.ts`), models, services, the contracts of its server routes, its English. |
| `mobile/<app>` | Each app's React Native project (`mobile/notes`: Carnet for Android, its own install). |
| `web/<app>` | Each app's web app (`web/notes`). |
| `server` | One server for the suite: the platform, and each app's module in `src/apps/<app>`. |

The packages are TypeScript sources with no dependency, compiled into every program (Hermes, the browser, Node) under one name each, `@unlease/<package>/…` (path aliases in each program's tsconfig, bundler and test runner); their order is enforced by lint: `core <- design <- notes <- programs`. The root is an npm workspace for the web apps and the server (one lockfile; the image installs only what they use); React Native pins its own React, ESLint, Jest and Babel, so each phone app keeps its own install, and Metro resolves what the packages' files import from the app's own `node_modules`.

Installing one app means: the server (one image, whatever the apps), and that app's clients (its APK, its web app). An app's clients only sync and show its own types today; reading another app's (to show a mention of an event in a note) is the next step, through the same sync, with a `types` list in the request.

## Data across apps

- **Record types belong to apps** (`core/sync/schema.ts`): each app declares its own with `defineRecordTypes` (Carnet's six, `note`, `check`, `link`, `label`, `attachment`, `block`, in `notes/sync/types.ts`): each field's check, the long text fields merged instead of overwritten (with their limit, and a merge of their own for drawings), the defaults a rollback writes back, the records every device seeds. Names are unique across the suite, so one store holds every app's records (the server's `records` table, the phone's SQLite table, the web's IndexedDB), and a type tells which app a record is.
- **Ids are UUIDv7** (`core/services/ids.ts`, RFC 9562): minted offline on any device, unique across every app, sorted by creation (a 48-bit millisecond time, a counter within the millisecond, random bits), and what iCalendar and vCard expect of a UID (RFC 7986 recommends a UUID). Records every device seeds keep fixed ids (`inbox`, the starter collections), so two devices make the same one.
- **References** (`core/refs.ts`): a type and an id. `REF_TYPES` lists what people can point at in the whole suite, each with its app and its record type: `note` (a collection is a note), `link`, `page` (a `block` of kind `page`) for Carnet; another app's things join it. A reference sits in rich text as a mention `{@type=id}` (`core/services/richText.ts`, the suite's text format) or in a block's `targetType`/`targetId` (bookmarks, embeds). A type a build does not know, written by a newer client, travels and stays as it is (the parser and the schema keep any well-formed type) and shows as unavailable, so an older phone never destroys what a newer app wrote.
- **The apps' registry** (`core/apps.ts`): every app, installed or not, with its id, name and slug (its databases, its storage, its phone links `<slug>://<type>/<id>`). `/api/health` lists the apps a server runs.

## The server's apps

The platform (`server/src/` outside `apps/`) runs the same for every app: the token, the sync, files and their display copies, settings, the Administration, backups to S3, the Seafile drive, the daily database copy. Each app adds its part as a `ServerApp` (`server/src/apps/types.ts`), listed in `server/src/main.ts`; the platform never imports an app's package. Carnet's (`server/src/apps/notes/`):

| Hook | Carnet's |
| --- | --- |
| `routes` | Sorting by Claude, the link modules, Seerr, questions about pages, Claude's spending (`routes.ts`) |
| `stored`, `start`, `stop` | The reading of new links, resumed at start, its queue drained at stop (`analysis/`) |
| `chores` | The bin emptied after a week (`bin.ts`) |
| `filesInUse` | Photos, link pictures and page files the collector keeps (`files.ts`) |
| `files`, `markdown`, `readme` | Its files' layout under `Carnet/` in Seafile and archives, its notes, collections and pages as Markdown (`files.ts`, `markdown.ts`) |
| push rules | A note restored after the bin emptied it comes back with what the purge took (`bin.ts`, given to the sync service) |

Backups hold every app's records in one `unlease.json` (`unlease-2026-10-26T03-00-00Z.tar.gz`), each app's Markdown and files under its own folder.

## Data and sync

- **Records:** every note, checklist item, link, label and photo is a record: a map of fields, each with the hybrid logical clock (`core/sync/hlc.ts`) of its last write.
- **Merge:** field by field, the larger clock wins (`core/sync/record.ts`). Commutative and idempotent, so devices converge whatever the order. Two offline edits to the same field keep the later one, except typed text.
- **Drawings** (a note of kind `drawing`, a page's `drawing` block) keep their strokes in a `drawing` field as text, one stroke per line (`notes/services/drawing.ts`: an id that sorts by time, the tool, size and ink, the points in units of a sheet 1000 wide, polyline-encoded). Strokes are only drawn or erased, never changed, so the field is merged as a set, not as words: everything either side drew stays, everything either side erased goes, in time order (`mergeStrokes`, chosen by `mergeField`). It travels as typed text otherwise (bases, `saveTypedText`, `saveBlockText(…, 'drawing')`). The sheet is as tall as what is drawn on it (`drawingHeight`), so a card or a block keeps its proportions without measuring.
- **Formatted notes:** a text note's `body` is plain text until its first mark or heading; then the note is `rich` for good and its body is lines, each a page's rich-text markup after an optional `# `, `## ` or `### ` (`notes/services/noteBody.ts`, saved by `saveNoteLines`, merged word by word as typed text). Everything but the editors reads a body through `bodyText` (the words: search, widgets, reminders, the clipboard) or `bodyMarkdown` (a backup).
- **Typed text:** a note's title and body, a checklist line and a link's comment (`MERGED_TEXT_FIELDS` in `core/sync/textMerge.ts`) are merged word by word when two devices change them before seeing each other's edit: edits in different places both survive; where both rewrote the same words, both versions are kept, the older first, as alternatives on one line (« mardi / jeudi ») or one after the other when they span lines. Rewrites a few shared words apart in one sentence count as one passage, so each version stays whole instead of interleaved word by word. A device keeps, beside each unacknowledged edit of such a field, the value it started from (its base, `core/sync/bases.ts`) and sends it with the push; the server merges a concurrent edit into one text under a fresh clock of its own; a device merges an edit that reaches it before its own is acknowledged; an editor merges what lands while someone types (`saveTypedText` in both apps' actions). A device's own earlier write is never merged with (its answer was lost: last writer wins), and when what the server holds descends from a version a device sent (a merge, or another device's edit on top of it), that version is the base of the device's next push (`MergeLineage`, in memory: a restart in between loses it). Texts too far apart to align by words merge by lines; a long passage both rewrote keeps the side that changed more.
- **Protocol:** one endpoint, `POST /api/sync` (`core/sync/protocol.ts`): the device pushes pending records (with the bases of their typed text) and receives everything after its cursor (the server's own sequence). With nothing to send, the request waits up to 25 s for news (long-poll), so a link read on the server or an edit on the web appears within a second.
- **Loop:** `core/sync/engine.ts`, shared. Pushes are paged by count and UTF-8 size; the server's answer is acknowledged before it is merged; a record edited during a request stays pending (acknowledgement compares clocks). A phone sent to the background or a hidden tab stops long-polling, but first sends what was just written. Offline, both retry with a growing wait, which ends the moment the network is back (the browser's `online`, Android's validated default network through the `Connectivity` module) or when the server names one (`Retry-After`).
- **Lost data:** the server names its dataset (`epoch`, in every answer); each daily snapshot gets a name of its own, so restoring one always counts as a new dataset. A device that has seen more than the server holds (another kind of backup restored, the data wiped) also makes it choose a new name: each start of the server is a run with a random id (`runs` in `meta`); every answer names the server's last sequence and its run (`head`, `run`), the device keeps them as one value and sends them back, so a head from a run the server never had, or outside its run, gives a restore away whoever syncs first, however far behind the device was, and whatever the dates say. The phone then also uploads its photos again (one the server has is answered at once); the web keeps no copy of a photo once uploaded. Every device that knew the old one, or was moved to another server, sends everything it holds again.
- **Clocks:** no single date is trusted, the server's included (a box without a battery-backed clock boots days behind until it gets the time). A device more than a minute behind the server writes on the server's time; it never follows the server backwards. Every request carries the device's time. Once another device has spoken since the server started, the server replaces a pushed clock more than a day ahead of the latest of what the other devices last said (moved on by the time since), the clocks they stored and its own date: a phone with the wrong date. Each source can only raise that bar, so a device or a server that is behind never gets the right clocks replaced. The device then takes back the server's clock for that same value (`adoptReplacedClocks`, any tab of the browser), so the field takes later edits. The bin counts its 7 days from the clock of the trashing write, not the device's `trashedAt`. A device more than 2 minutes off the server says so in its sync status (`clockNote`).
- **Phone storage:** records are JSON documents in one SQLite table (`mobile/notes/src/data/db/migrations/001_initial.ts`, bases since `002_bases.ts`, every record type since `003_every_type.ts`: a type the table refused made the records pulled with it skipped), read into memory at boot. This departs from the house rule of typed columns on purpose: the merge works on field maps, nothing aggregates in SQL, and a field written by a newer client must survive a round trip through an older one. The server stores records the same way, commits with `synchronous = FULL` (a device stops resending a change once told it is stored) and writes a consistent copy of its database every day (`backups/`).
- **Ordering:** fractional index keys (`core/services/fractionalIndex.ts`): moving one item rewrites one record. Two devices adding at the same place mint the same key (ties sort by id); an insert or a move between tied neighbours also gives the later twin a new key in the same batch (`placeAt`), and `positionBetween` never throws on them. That new key is a write like any other: a twin dragged elsewhere at the same time ends where the later of the two writes put it.
- **Deletion:** a `deletedAt` tombstone, never a removed row. The bin empties after 7 days (server job); a note a device restores after the bin emptied comes back with what the purge took (its photos are kept 30 days for that), unless a person deleted it for good.

## Link reading

1. A link saved from the share sheet or the quick input lands in "Non classé" with `status: 'pending'` and `autoFile: true`.
2. The server fetches the page (SSRF guard, a link-preview user agent when blocked, oEmbed for video and music sites), extracts meta tags, JSON-LD and text, and asks Claude once for a structured result: title, the site's name as people write it, kind, summary, price, key facts, best image, and the collection it belongs in. A page the server cannot read, Claude fetches itself (`web_fetch`); its pictures then come from what that fetch returned.
3. It keeps up to three images as WebP blobs, then writes everything in one change; the phone's long-poll returns and the transfer panel shows where the link went. With no server, or a server without a key, links are kept plain (`skipped`) from the start: nothing waits on a reading that cannot happen.

4. **Sorting saved links** (`POST /api/sort`, `notes/sync/sorting.ts`): the app sends links as their reading left them (no page is read again) and the collections with their sentence and newest titles (`sortTargets`, from which the server files a new link too). The server asks Claude in batches of 60 (3 at a time) and answers moves by id; after a failed batch, or once the budget is spent, no new batch starts and the moves of those that answered come back marked `incomplete`. The app writes them as one undoable batch, skipping a link moved meanwhile, and runs one sort at a time. `file` puts a link where it clearly belongs or leaves it ("Ranger Non classé", a new collection taking from Non classé, the links of collections deleted from their page or a board selection); `review` lists what no longer belongs in a collection, for the person to keep or untick. A call counts toward the monthly budget, not toward the links read (`analyses.task`).
5. **Who filed it:** a link's `filedBy` is `claude` when Claude chose its collection, `person` when the person did (moved it, added it to a collection, kept a review's move, sent a deleted collection's links to another), null when it landed in Non classé by default. "Ranger Non classé" leaves the person's choices alone. A link shared again within 30 days, its first copy deleted since, is filed from cache into the same collection by id, renamed or not.
6. **Once per collection** (`notes/services/savedLinks.ts`, `addLinks` in both apps): an address a collection holds already (trackers aside) is not added to it again; one another collection holds is added with that link's reading copied (`ready`, the same image blobs), so the page is not read twice. Filed by Claude, an address any live collection holds is not added at all (it would land beside itself). A slip says which.
7. **Link modules** (`notes/models/modules.ts`, `notes/services/modules.ts`): small tools a collection shows on its links, picked per collection in the synced note field `modules` (null keeps `DEFAULT_MODULES`; unknown keys from a newer client pass through). A module shows on a link when the collection picked it, it fits the link (`moduleFits`: its kind, a price, an address, not stamped done) and what it needs is there (`moduleWorks`: nothing, a server, Claude, or Seerr linked on the server). Both apps put them in one row of small buttons under the link's title (`ModuleBar`) and manage them from the collection's menu ("Modules"). Promo codes (`POST /api/coupons`) and offers elsewhere (`POST /api/offers`, market `new` or `used`) are Claude with `web_search` (5) and `web_fetch` (2), basic versions on Haiku, no structured format (web search always cites, and citations cannot go with one), the JSON read from the text after the last tool block (`server/src/apps/notes/analysis/searches.ts`): kept six hours by task, normalized address and language, a running search joined, a search outlives the app hanging up and stops at 90 s, billed at $0.01 a search on top of the tokens, a call cut off billed at a whole search's estimate. Ratings (`POST /api/ratings`, kept a week), a series' recap up to the episode the person stopped at (`POST /api/recap`, kept a month under the address marked with the stop, `#s2e5`, so each stop has its own answer) and other outlets on an article's story (`POST /api/coverage`, kept half a day) go through the same `LinkSearches`, each with its own prompt (`prompt.ts`). A question about a link (`POST /api/ask`, `questions.ts`) sends Claude the page's words (its article whole when one stands out, up to 30 000 characters), with web search only when the person ticks it (3 searches); nothing is kept, the same question at once is joined, and a page gone for good (a 404) is never paid for unless the web may answer. A recipe's ingredients and method (`POST /api/recipe`, `recipe.ts`) come from its structured data (`recipeIngredient`, `recipeInstructions` as text, steps or sections), free, else from Claude reading the page; the cook mode asks for the steps (`steps: true`), so a page whose data lists ingredients but no method costs Claude once, then it is kept a month, a method Claude found missing included (`stepsRead`); one reading runs per address (the list joins any, the cook mode one that looks for the method, else asks again once it ends), the read and Claude share one 85 s deadline, a page gone for good is never sent to Claude, and the cook mode falls back on the ingredients kept when the page cannot give more; a method written as one block is cut into steps before each « Étape n », else by sentences. Seerr (`POST /api/seerr`, `server/src/apps/notes/seerr.ts`) is the server calling the address the Administration gave, with a plain fetch (it is often on the local network) that never follows a redirect, its key sent only once the address has answered `/api/v1/status` as Seerr (dropping the key tries nothing): with the key it searches TMDB's titles there and picks the link's kind and year, without it the answer is Seerr's own search; the apps remember Seerr's address with the server's settings, ask once every few minutes per link, and open Seerr's search if it does not answer. "Pour N personnes" and the cook mode's timers live in each app's memory (`kitchen.ts`: a factor per recipe, scaled in core by `scaleIngredient`; durations found by `stepTimers`); the web keeps the screen on with the Wake Lock API and chimes a rung timer, the phone keeps the screen on natively and schedules each timer as a notification. "Garder une copie" (`POST /api/copies`, `article.ts`, `copies.ts`) is the server alone: the page's main content as block drafts, its pictures kept as `link` blobs; the app makes the page (`createPageFrom`, one batch), the link's bookmark card first, which is how it finds the copy again (`copyOf`). "Y aller" is a Google Maps directions address built in core (`directionsUrl`); "Liste de courses" writes a checklist in one batch (`addToChecklist`). Each module's runs are rows of `analyses` under its own `task` (`ModuleTask`: `recipe` for both recipe modules; migration 7 dropped the CHECK so a new module needs no table copy).

The Claude key, model and monthly budget are server settings changed from the apps (`GET/PUT /api/settings`). Without a key, links are kept as plain links (`skipped`); the settings screens offer to read them once a key is set.

## Administration: backups and files

The server's settings live in the apps' Administration (web `/admin`, phone `Admin`), apart from the device's Réglages: the server's address and token, link reading by Claude, the S3 backup and the drive. The wording of their statuses is shared (`core/services/admin.ts`); the routes and statuses are `core/sync/admin.ts`.

- **Backups to S3** (`server/src/backup/`): on a schedule (`6h`, `daily` by default, `weekly`) or on demand, a readable archive (`unlease.json` with every record of every app and its clocks, each app's Markdown under its folder, for Carnet every note, collection and page, `LISEZMOI.md`) and each photo and file once (`fichiers/<id>.<ext>`, an upload's original only), except those Seafile holds: files live there only, and `unlease.json` says where. A small SigV4 client, path-style, trying again what S3 could not answer; the archive is tar.gz, streamed both ways. Each run lists what S3 holds, so a file lost there is sent again. The newest snapshots this server made are kept, never another server's; a file goes once no live record points at it and no kept snapshot names it. Nothing is backed up while the server holds nothing (a new server about to be restored), nor during a restore. Settings are tried before they are kept (list, write, delete).
- **Restoring** an archive from S3 or a downloaded one (a full archive holds the files): `merge` keeps each record's own clocks, so only what the server lacks comes back; `rollback` writes the backup's values under fresh server clocks, so they win on every device, and keeps what was created since. A server holding nothing but "Non classé" always merges; its devices then send back what is newer. A file comes back when what a backup keeps of it (the original) is missing, even if a display copy is here: from the archive, from Seafile where the backup says it is (nothing copied or sent again), else from S3.
- **First run** (`core/services/setup.ts`, both apps' `SetupScreen`): one decision (the server's address and token, or the notes kept on this device), the device's colours and ground, then, only on a server that held nothing when the device came, « Votre serveur »: the Administration's own sections as rows, each optional and opened from its row: a restore first (the newest snapshot chosen, always a merge; notes from S3, files from Seafile), Claude, S3 (starting from Scaleway Paris), Seafile, Seerr. A device joining a server already in use goes from its colours straight to the board.
- **Durability:** blob files are flushed to the disk before they are renamed into place and their row committed; the phone's SQLite commits with `synchronous = FULL`; the web asks the browser to keep its storage (`navigator.storage.persist`).
- **Files in a drive** (Seafile, `server/src/drive/`): originals of photos and page files live in a folder of one library (`/Unlease` by default), under each app's own folder and named after what holds them (Carnet's notes and pages: `server/src/apps/notes/files.ts`, also the archives' layout); renames move them, the collector's removals delete them. The server keeps the display copies and streams an original from Seafile when asked; a file already in place (a server restored, its Seafile kept) is taken, never uploaded twice. Turned off, the drive gives every original back before it is forgotten.

## Pages

A Notion-like knowledge base, on the web and the phone, in a space of its own beside the notes on both.

- **One record type:** every page and every block in it is a `block` record (`notes/models/blocks.ts`). `parentId` is its container (a page, a column, the item it is nested under, a table for its rows), null for a top-level page; `position` orders siblings (`placeAt`). A sub-page is a `page` block in its parent's content, so the navigation's tree and the content are one structure and a move is one write. Kind-specific fields are written only when a block uses them.
- **Rich text:** a text block's `text` is one markup string (`core/services/richText.ts`: runs such as `{b,fg=red:mots}` (keys are the mark `k`), mentions `{@note=ID}`, `{@link=ID}`, `{@page=ID}`, dates `{@date=2026-10-28}` or `{@date=2026-10-28T1430}`), so it merges word by word as typed text (`MERGED_TEXT_FIELDS.block`, saved with `saveTypedText('block', …)`). The parser never throws: a merge may cut a run, and a date that is no real day is its characters. A mention and a date are one character in every offset; a date is shown relative to today (`core/services/dates.ts`) and written as its day wherever words must stay true (a search, a copy, Claude).
- **Table of contents:** a `toc` block holds nothing: it lists the page's headings as they are (`pageHeadings`, into columns and toggles, never into a sub-page).
- **Page actions** (`web/notes/src/app/store/pages.ts`): each is one `writeLocal` batch recorded in the page's history (`pageHistory.ts`): undo and redo write the other values with a newer clock, and typing joins a burst under 1.5 s. Blocks dropped beside another make a `columns` block of `column`s (each with a `ratio`); a set left with one column dissolves (`tidyColumns`).
- **Tables:** a `table` block holds its typed `columns` (an unknown type key reads as text) and `row` children whose `cells` are keyed by column id; a type change converts the cells (`convertCell`, `notes/services/table.ts`).
- **Captions:** a code block, a table, a media, a bookmark or an embed (`CAPTION_KINDS`) may carry a `caption`, one line of plain text merged as typed text (`saveBlockText(…, 'caption')`). A block turned into a kind that takes none loses it.
- **Mentions, bookmarks, embeds** point at a note (a collection is a note of kind `links`), a link or a page by id and show it as it is now; a deleted one reads as gone. Notes, collections and links open in a new tab, pages in place. A text holding one mention and nothing else, a bookmark and an embed switch between the three in place from the grip (`shownTarget`, `showTargetAs`); a page is never offered as an embed.
- **An embedded collection** shows as a list or a table (`view`). The table's columns are its links' fields and the facts Claude read (`notes/services/collectionTable.ts`); each embed keeps their order and which are shown (`viewColumns`). No column is added, and a row is a link added to the collection. It shows the links to do; with `showDone`, those done follow under « Déjà faits », as on the collection's screen.
- **Files:** a picture goes through the photo route, which makes its display copy; a video, a PDF or any other file through `PUT /api/files/:id`, kept as sent (100 MB at most; served as `application/octet-stream` unless it is an image, a video, audio, a PDF or plain text). The browser keeps its copy until the server has it, as for photos, and `uploaded` tells other devices when to show it. The blob collector keeps every file a block points at.
- **Bin:** a page in the bin (`trashedAt`) takes everything under it and reads as it is. After 7 days the server tombstones it and every block under it, except a sub-page put in the bin on its own, which waits for its own week.
- **Per browser, never synced** (`pagesUi.ts`, localStorage): the tree's open branches, the toggles open, the last page read.
- **Questions to Claude** (`notes/services/pagesAsk.ts`, `notes/sync/pagesAsk.ts`, `POST /api/pages/ask`, `server/src/apps/notes/analysis/pagesAsk.ts`): off until the Administration turns them on (`ServerSettings.pages`: `enabled`, `everywhere`, `web`, `reach`). The device builds what a question reads (`askContext`): the page, the page and its whole tree of sub-pages, or every page ranked by the search engine against the question (the page asked from first, then the hits, then the most recently changed), each page as its blocks in Markdown (a table a piece per row, embeds and bookmarks as what they show, a sub-page named), within `PAGES_REACH_CHARS[reach]`; a page that does not fit is read in part and the rest left out, and the server refuses more. A page with `private` (synced on the block, set from its menu) and everything under it is never read, nor a page in the bin. The server sends each page as a `search_result` (source `carnet-page:<id>`, title its path, one text block per block) with citations on and the pages cached (`cache_control` on the last), the earlier turns as plain messages after it, the web tool only when asked and allowed; Claude's `search_result_location` citations come back as the blocks they span (`pagesAnswer`), the web's as sources. Labels sent to Claude are fixed English; nothing is kept, the same question at once is joined, each run is billed under task `pages`, and a run cut off is billed as the app foresaw it (`askCost`). Each app holds the conversations in memory, one per page (`pagesAsk.ts`); a source opens its page at the block (the web's `#block-<id>`, the phone's `block` route parameter), and an answer laid in a page is a toggle titled with the question, the cited pages as mentions under it (`answerDraft`).
- **Phone:** the same records and gestures: the library indexes blocks as the web's does (`blocks`, `blocksByParent`), and `mobile/notes/src/app/store/pages.ts` and `pageHistory.ts` mirror the web's (change them together). Text is typed in native fields that draw the runs; an edit is read against the selection it was made on and mapped back onto the runs (`core/services/richDisplay.ts`), a mention shown as its name and taken whole. Pictures go through the photo route, other files through `PUT /api/files/:id` (`mobile/notes/src/app/pageFiles.ts`, sent by the sync loop); an uploaded video, PDF or file is opened from the web for now (the server serves files with the token in a header only). Its device-only state (open branches, open toggles, the last page) is a preference (`pagesUi.ts`).

## Search

- **The spotlight** (web: ⌘P or Ctrl+P, and Ctrl+K): an in-memory full-text index in core (`core/services/searchIndex.ts`) over every live page, note, collection and link (`notes/services/spotlight.ts`: a page's blocks, a note's lines and checklist items, a link's reading and comment; labels, sites, kinds and collections as meta). A new text worth finding is added there.
- **Matching:** words folded as everywhere (`foldText`), found whole, by their start, in the plural, inside a longer word (four letters or more) and by a title's initials; with one typo from four letters (two from eight) only when the words as typed find fewer than eight hits. A word of one or two letters finds titles by its start, the content only whole. Every word is required but the small ones (« de », "the"); `"…"` keeps words together, `-word` leaves out.
- **Ranking:** the titles that answer alone first, then the content (BM25F over title, headings, body and meta, the best few weighed again for how close their words sit, a little for a recent change), then, when nothing holds every word, what holds the most, saying what it lacks. What this browser opened lately, or picked for the same query, lifts a result within its tier (`web/notes/src/app/store/spotlight.ts`, localStorage, never synced).
- **Index:** built again after each change of the library, a document whose words did not change keeping its entry, and once while the browser is idle after the start. The board's search box (`/`) and the phone keep their simpler matching (`core/services/search.ts`, `pageSearch.ts`).

## Interface language

French or English, chosen per device in Réglages (`locale` in each client's settings). `core/i18n` holds the language and `t()`: the French sentence is the key, the English comes from the dictionaries each program adds at start (core's in `core/i18n/en/`, the design system's in `design/i18n/en.ts`, Carnet's in `notes/i18n/en/`, one part per area), and a sentence without English shows in French. `tools/i18n/check.mjs` checks that each package's sentences have their English in a dictionary that package can count on, so an app installed alone never lacks another app's. The formatting helpers (`core/services/format.ts`: dates, numbers, prices, `plural`) follow it. A new language draws every screen again where it was: the web remounts the app on the same address (`LocaleRoot`), the phone remounts its navigation with the stack it had. Until one is chosen, a device takes its own system's language (French when it is French, English otherwise). The server never sets a language for its own words: its messages stay French and the apps translate the fixed ones they show (`en/server.ts` in core's dictionary and in Carnet's). What Claude writes follows the link: a link carries `lang`, the interface language of the device that saved it (set again when it is read again), and the server names it on the first line of its message to Claude; a cached reading is reused only in the same language. Android's own strings (widget picker descriptions) follow the system.

## Phone specifics

- **Board:** a masonry wall of paper sheets: each card is exactly as tall as what it shows, computed from its anatomy and Signika's advance widths, never measured (`notes/services/wall.ts`, `textWrap.ts`), so the wall is virtualised without a layout pass and the text is cut to the lines that were counted.
- **Native modules** (`mobile/notes/specs/`, `mobile/notes/android/.../intake`, `.../media`, `.../haptics`): the share target (text and images, copied into app storage before the grant lapses), the photo picker and camera (images re-encoded upright, at most 2560 px), the Keep Takeout zip (only `Keep/` entries, zip-slip safe), and the system's own haptic clicks for gesture thresholds and long presses (no vibration permission).
- **Reminders** are armed on the phone with Notifee from the synced `reminderAt` (`mobile/notes/src/app/hooks/useReminders.ts`); exact alarms when Android allows it. The phone syncs only in the foreground, so a reminder set on the web is armed the next time the app is opened (an answer from the notification's buttons is sent at once, `flushNow`).
- **Widgets** (`mobile/notes/android/.../widget`): Actions rapides and Classer un lien hold no data; Collection, Notes d'un label and Note draw what JavaScript hands them. `mobile/notes/src/app/widgetPayloads.ts` builds each placed widget's picture as JSON, with the app's wording and order; `mobile/notes/src/app/widgets.ts`, started by `bootstrap` wherever JavaScript runs, sends it again 400 ms after the library changes, through the `Widgets` module. The native side only draws (RemoteViews) and routes taps: `carnet://` links into the app, a website through `WidgetRouterActivity`.
  - **Ticks** on the Note widget show at once, wait in the native store, and are written by JavaScript as one change (`setChecks`): in a headless task started from the broadcast (`WidgetTasks.kt`, `widgetTask.ts`; a closed app may not start a service), or at the next start.
  - **The quick window** (`QuickActivity`, the `quickWindow` root): the link field and the pickers, drawn by the app over the home screen, its window the scrim; also the launcher's configuration step when a widget is placed.
  - **Look:** colours, continuous-corner sheets (corner vectors and bands, as a launcher cannot clip), pebbles, emblems and glyphs come from `design` through `tools/widgets/build_widget_resources.mjs`. A widget is a slab of the ground: its two tones down the middle band, under the web's film grain (`tools/textures/build_grain.py`, both themes); its sheets carry the paper's speckle at the theme's strength. The grain is laid in pieces that step along each corner's curve, since a tile cannot be clipped. A launcher cannot load an app's font: titles are set in Signika by the app as tinted images (`WidgetType.kt`), the rest is the system font. Link pictures are fetched with the device's token and cut to their frame (`Thumbnails.kt`).

## Deployment

One image (root `Dockerfile`, published by `.github/workflows/image.yml` as `ghcr.io/stephenprn/unlease` for amd64 and arm64) builds the server and the web apps; the server serves the web build at `/` and the API at `/api` on one port (`server/src/http/web.ts`, `UNLEASE_WEB_DIR`), so the app and its API share an origin and need no CORS. The web app recognises a server serving it (`/api/health` on its own origin) and fills in its address. The same build also works from any static host, then with `UNLEASE_CORS_ORIGINS`. `docker-compose.yml` and `docs/SELF-HOSTING.md` are the reference deployment; the APK is attached to each release by `.github/workflows/android.yml`.

## Web specifics

- **Storage:** records in IndexedDB, written behind memory a tick later (a failed write is retried); tabs share one database and post what they write, pending marks and bases included, on a BroadcastChannel.
- **Offline:** a service worker (`web/notes/public/sw.js`, production builds) keeps the page, its hashed assets and the fonts, so the installed app opens without a network and works from IndexedDB; it never touches the server's origin.
